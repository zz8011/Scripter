## 二、技术选型决策

### 2.1 ORM 框架：Drizzle vs Prisma

| 特性 | Drizzle | Prisma |
|------|--------|--------|
| **性能** | ⚡ 快（无查询解析开销） | 中等 |
| **包大小** | ~100KB | ~3MB |
| **SQL 控制** | ✅ 显式、透明 | 隐式抽象 |
| **Edge Runtime** | ✅ 完全支持 | ❌ 不支持 |
| **TypeScript** | ✅ 原生类型安全 | ✅ 生成类型 |
| **学习曲线** | 中等 | 较低 |

#### 决策：Drizzle ORM

**理由**：
1. 性能优势明显，无查询解析开销
2. 包体积小（~100KB vs ~3MB）
3. SQL 控制透明，便于优化
4. 完全支持 Edge Runtime

**影响**：
- 需要 SQL 基础知识
- 查询构建需要手动编写
- 迁移需要手动管理

---

### 2.2 认证系统：Casdoor vs NextAuth.js

| 特性 | Casdoor | NextAuth.js |
|------|---------|-------------|
| **部署方式** | ✅ 独立服务 | 应用内集成 |
| **管理界面** | ✅ 完整 Web UI | ❌ 无 |
| **SSO** | ✅ 内置 | ⚠️ 需自建 |
| **多租户** | ✅ 原生支持 | ❌ 需自建 |
| **协议支持** | OAuth 2.0 / OIDC / SAML | OAuth 2.0 / OIDC |
| **集成复杂度** | 中等 | 较低 |

#### 决策：Casdoor

**理由**：
1. 企业级身份管理功能完整
2. 可视化管理界面降低运维成本
3. 支持多种协议和 SSO
4. 独立部署，解耦认证逻辑

**影响**：
- 需要独立部署 Casdoor 服务
- 集成需要配置回调 URL
- 需要了解 OAuth 2.0 流程

---

### 2.3 AI 模型：智谱 GLM-4.7 vs 其他方案

| 特性 | 智谱 GLM-4.7 | OpenAI GPT-4 | Vercel AI SDK |
|------|--------------|-------------|---------------|
| **成本** | ¥0.50-4/百万tokens | ~$30/百万tokens | 依赖上游 |
| **中文能力** | ✅ 专门优化 | 一般 | 依赖上游 |
| **国内合规** | ✅ 合规 | ❌ 需处理 | ❌ 需处理 |
| **API 稳定性** | ✅ 国内节点 | ⚠️ 可能受限 | ⚠️ 可能受限 |
| **流式响应** | ✅ 支持 | ✅ 支持 | ✅ 支持 |
| **函数调用** | ✅ 支持 | ✅ 支持 | ✅ 支持 |

#### 决策：智谱 GLM-4.7

**理由**：
1. 成本降低 95%+（¥0.5/百万tokens vs $30/百万tokens）
2. 中文能力专门优化
3. 国内访问稳定，无合规风险
4. API 功能完整（流式、函数调用）

**影响**：
- 需要适配智谱 API 格式
- Prompt 可能需要调整
- 需要配置 API 密钥管理

### 2.4 编辑器框架：TipTap vs 其他方案

| 特性 | TipTap | Slate | Monaco | Quill |
|------|--------|-------|--------|-------|
| **无头设计** | ✅ | ✅ | ❌ | ❌ |
| **剧本扩展** | ✅ 成熟 | 需自建 | ❌ | ❌ |
| **React 集成** | ✅ 原生 | ⚠️ 社区方案 | ✅ | ✅ |
| **实时协作** | ✅ 支持 | ⚠️ 需自建 | ❌ | ⚠️ 需自建 |
| **学习曲线** | 中等 | 较高 | 较低 | 较低 |
| **包大小** | ~100KB | ~150KB | ~2MB | ~200KB |

#### 决策：TipTap

**理由**：
1. 无头设计，高度可定制
2. 已有成熟的剧本格式扩展
3. React 集成良好
4. 支持实时协作（未来需求）
5. 社区活跃，文档完善

**影响**：
- 需要自定义场景标题、对话、动作描述节点
- 编辑器状态管理需要特别设计
- 学习曲线中等

### 2.5 拖拽库：@dnd-kit vs 其他方案

| 特性 | @dnd-kit/core | react-beautiful-dnd | react-dnd |
|------|---------------|---------------------|-----------|
| **维护状态** | ✅ 活跃 | ❌ 已废弃 | ✅ 活跃 |
| **性能** | ✅ 优秀 | ✅ 良好 | ⚠️ 一般 |
| **虚拟滚动** | ✅ 支持 | ⚠️ 有限 | ❌ 不支持 |
| **TypeScript** | ✅ 原生支持 | ✅ 支持 | ⚠️ 社区方案 |
| **API 设计** | ✅ 现代化 | ✅ 简洁 | ⚠️ 复杂 |
| **可访问性** | ✅ 完整 | ✅ 完整 | ⚠️ 有限 |

#### 决策：@dnd-kit/core

**理由**：
1. 现代化 API，TypeScript 原生支持
2. 性能优秀，支持虚拟滚动
3. 可访问性完整
4. 文档清晰，社区活跃

**影响**：
- 需要配置 DndContext provider
- 拖拽手柄需要自定义样式
- 金色插入指示线需要自定义

## 三、架构设计

### 3.1 整体架构

```
┌─────────────────────────────────────────────┐
│                   前端层                      │
│  Next.js 14 (App Router)                     │
│  ├── shadcn/ui + Tailwind CSS               │
│  ├── TipTap 编辑器                           │
│  └── @dnd-kit 拖拽                           │
└─────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────┐
│                  业务逻辑层                   │
│  ├── Server Actions                         │
│  ├── API Routes                             │
│  └── Middleware                             │
└─────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────┐
│                  数据访问层                   │
│  Drizzle ORM                                 │
│  ├── Query Builder                          │
│  └── Schema Definitions                      │
└─────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────┐
│                  数据存储层                   │
│  PostgreSQL 15+                              │
│  └── 数据持久化                              │
└─────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────┐
│                  外部服务层                   │
│  ├── 智谱 GLM-4.7 (AI 文本)                 │
│  ├── T8Star (AI 图片)                        │
│  ├── Casdoor (认证)                          │
│  └── S3 / OSS (文件存储)                     │
└─────────────────────────────────────────────┘
```

## 六、版本管理

### 6.1 版本规则

**格式**: `v{major}.{minor}.{patch}`

| 类型 | 说明 | 示例 |
|------|------|------|
| **Major** | 技术栈重大变更 | v1.0 → v2.0 |
| **Minor** | 新增技术组件或版本升级 | v1.0 → v1.1 |
| **Patch** | 版本号更新或小修正 | v1.0.0 → v1.0.1 |

### 6.2 变更流程

```
1. 发现技术栈需要调整
       ↓
2. 技术团队评估影响
       ↓
3. 更新技术栈文档
       ↓
4. 团队评审
       ↓
5. 发布新版本
       ↓
6. 更新所有引用本文档的材料
```
