# AgentScheduler.ts 代码审查报告

> 审查日期: 2026-02-02  
> 审查重点: 任务调度算法、定时器管理、优先级队列、内存泄露、并发安全性

---

## 代码质量评分

**6/10**

代码整体结构清晰、职责集中，但在调度策略、计时器生命周期、队列可扩展性和资源回收方面还有明显改进空间。

---

## 主要问题（按影响度排序）

### 1. 调度器注册顺序问题
- **位置**: 构造函数
- **问题**: 构造函数里直接调用 `agentBus.subscribe(this.agentId, ...)`，但注释已说明 scheduler 还未注册，可能直接抛错
- **风险**: 高

### 2. 吞吐量硬编码限制
- **位置**: `processTasks()` 方法
- **问题**: `setInterval` 每 100ms 只取 1 个任务执行，吞吐量被硬编码限制；高并发场景会积压
- **风险**: 中高

### 3. 无并发上限控制
- **位置**: `executeTask()` 方法
- **问题**: 一直向 agent 发任务，可能同时运行过多任务导致资源打爆
- **风险**: 高

### 4. 任务取消/超时通知缺失
- **位置**: `cancelTask()` / `handleTaskTimeout()` 方法
- **问题**: 取消运行中任务仅清理本地计时器并删除 Map，但不会通知实际 worker 取消
- **风险**: 中

### 5. 内存泄漏风险
- **位置**: `stop()` 方法
- **问题**: 停止调度器时不取消订阅，`AgentScheduler` 被释放后仍可能被 `AgentBus` 引用
- **风险**: 中高

### 6. 队列无界增长
- **位置**: `enqueueTask()` 方法
- **问题**: 任务队列无容量或过期策略，长时间高负载会无限增长
- **风险**: 中

### 7. 优先级队列性能问题
- **位置**: `enqueueTask()` 方法
- **问题**: 优先级队列为数组线性插入（O(n)），任务量大时性能退化明显
- **风险**: 中

### 8. 竞态条件风险
- **位置**: `processTasks()` 方法
- **问题**: JS单线程异步重入仍有竞态风险，未使用 `isRunning` 保护
- **风险**: 中低

### 9. ID生成方式
- **位置**: `generateTaskId()` 方法
- **问题**: 使用 `Date + Math.random` 碰撞概率极低但不理想
- **风险**: 低

### 10. 类型兼容性
- **位置**: 定时器类型定义
- **问题**: Node环境下使用 `NodeJS.Timeout`，建议用 `ReturnType<typeof setTimeout>`
- **风险**: 低

---

## 改进建议

### 架构层面
1. **注册顺序优化**: 将 `subscribe` 移到 scheduler agent 注册之后，或在 `start()` 中完成注册与订阅
2. **并发控制**: 用可配置的并发上限（例如 `maxConcurrent`），按余量批量调度
3. **队列优化**: 改成可插拔的优先级队列实现（binary heap / Fibonacci heap）
4. **背压机制**: 提供 `clearQueue()` 或停止时清空队列的选项，设置队列最大长度

### 代码层面
1. **取消/超时通知**: 提供明确的终止消息（`CANCEL_TASK` / `TASK_TIMEOUT`）
2. **日志统一**: 统一日志出口（logger），避免直接 `console.*`
3. **ID生成**: 使用 `crypto.randomUUID()` 或可插拔 id 生成器
4. **类型兼容**: 使用 `ReturnType<typeof setTimeout>` 替代 `NodeJS.Timeout`

---

## 最佳实践建议

1. **调度策略接口化**: 将调度策略（FIFO/优先级/加权）抽成接口，便于替换测试
2. **计时器集中管理**: 计时器管理用集中式 registry，并在 `stop()`/`dispose()` 全量回收
3. **监控指标**: 增加监控指标：队列长度、吞吐量、平均等待时间、超时率
4. **单元测试**: 增加单元测试：优先级顺序、超时回收、取消行为、并发限制
5. **竞态保护**: 关注异步竞态，考虑原子操作或锁机制确保任务队列状态一致
6. **资源清理**: `stop()` 应取消所有订阅与清空任务队列

---

## 总结

整体代码稳定性适中，但改进内存管理、调度策略和日志有助于提升健壮性和性能。建议优先处理：

1. 修复调度器注册顺序问题
2. 实现并发上限控制
3. 优化优先级队列实现
4. 完善资源清理机制
5. 增加背压机制防止队列无限增长
